MQTT Cloud Dashboard with Relay Control

This project extends local ESP32 control to the internet. An ESP32 connects to Adafruit IO over Wi-Fi and uses MQTT to receive commands from a cloud dashboard. The board translates a command into a GPIO output for a relay module, which switches a connected lamp. This demonstrates how a dashboard, cloud messaging service, embedded device, and physical output can work together.

How the system works

Dashboard → Adafruit IO MQTT broker → ESP32 → GPIO → relay → lamp

  1. The ESP32 joins Wi-Fi and establishes an MQTT connection to Adafruit IO using its device credentials.
  2. The device subscribes to the feed used for relay commands. The dashboard publishes a value such as ON or OFF to that feed.
  3. The broker forwards the published message to connected subscribers, including the ESP32.
  4. The ESP32 checks the received value and sets its relay-control GPIO to the corresponding state.
  5. The relay switches the connected load. The firmware can then publish the resulting state to a status feed for the dashboard to display.

MQTT uses a broker to route messages between publishers and subscribers. The dashboard publishes a command; the ESP32 subscribes to the relevant feed. Neither needs a direct network connection to the other, which makes it easier to add more devices or dashboards later.

Dashboard and device feedback

The Adafruit IO dashboard provides the remote control interface. A control widget publishes the relay command, while status widgets can show whether the ESP32 is connected and what state the relay reports. A feed can also retain a history of reported values or control events, depending on the dashboard and firmware configuration.

Command and status are separate responsibilities: sending ON requests a change, while a status message reports what the device has applied. Keeping these distinct helps the interface reflect device feedback instead of treating a button press as proof that the load changed.

Why MQTT instead of local HTTP?

The previous HTTP project served its control page from the ESP32 and worked when the browser and board were on the same local network. This project routes messages through a cloud broker, so a dashboard can reach the device from another network when both the ESP32 and dashboard have internet access and valid credentials.

Relay control and safety

The ESP32 GPIO is a low-voltage control signal. It does not power the lamp; it controls the relay module, whose contacts switch the load. The relay and its isolation are central to the design, but they do not make exposed mains wiring safe by themselves.

Because the demonstration involves a 230 V AC load, mains-side construction and inspection must be handled by a qualified person using properly rated, enclosed components and appropriate protection. Disconnect power before any service. Keep the mains circuit physically separated from the ESP32 and low-voltage wiring, and do not expose this prototype as a finished household installation.

Engineering concepts demonstrated

  • Embedded networking: connecting an ESP32 to Wi-Fi and maintaining a cloud connection.
  • MQTT messaging: using a broker, feeds, publishers, and subscribers to route commands.
  • Device state: translating messages into GPIO actions and reporting status back to a dashboard.
  • Cloud monitoring: using dashboard widgets and feed history to observe device activity.
  • System integration: linking software, cloud services, a microcontroller, a relay, and a physical load.

Outcome and next steps

The project demonstrates an end-to-end cloud control path: a dashboard command travels through an MQTT broker to an ESP32, which controls a relay output. It builds on the local HTTP exercise by introducing broker-based messaging, remote access, and cloud-visible device state.

Possible next steps include adding more devices and feeds, monitoring sensors or energy use, showing connection-loss states clearly, and improving credential management. A production system should also define safe startup behavior, handle broker disconnections and invalid commands, protect dashboard access, and use hardware rated for the intended load.
