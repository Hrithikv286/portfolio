Task 5 — Forge: Firebase & Real-Time Integration

1. Objective

To build a cloud-connected smart environment using an ESP32, where a DHT11 measures temperature and humidity, an LDR measures light intensity, sensor readings are stored in Firebase Realtime Database, and the Task 4 web dashboard displays the data in real time. The dashboard also controls a relay-driven bulb manually or automatically.

2. Project Overview

Task 5 — Forge closes the loop between the physical hardware and the web dashboard. The ESP32 collects real-world sensor data and sends it to Firebase, while commands from the dashboard are received by the ESP32 and used to control the bulb through a relay.

The system is divided into three stages:

5.1 Sensors & Relay — Connect and test the DHT11, LDR and relay with the ESP32.

5.2 Firebase Backend — Configure Firebase Authentication and Realtime Database.

5.3 Integration — Connect the ESP32, Firebase and Task 4 dashboard into one complete real-time system.

3. System Flow

Sensors → ESP32 → Firebase Realtime Database → Web Dashboard → User

Dashboard controls → Firebase → ESP32 → Relay → Bulb

The ESP32 runs a continuous cycle approximately every 2 seconds. It reads the Firebase control settings, reads temperature, humidity and light intensity, determines the relay state according to manual or automatic mode, and writes the latest sensor reading to Firebase. The dashboard listens for database changes and updates the interface without requiring a page refresh.

5. Pin Configuration

DHT11 DATA → GPIO 4

LDR analog output → GPIO 34

Relay IN → GPIO 26

DHT11 VCC → 3.3 V

DHT11 GND → GND

GPIO34 is used for the LDR because it belongs to ADC1, which can be used reliably while Wi-Fi is active. A 10 kΩ resistor is used with the LDR to form a voltage divider. A bare 4-pin DHT11 requires a pull-up resistor on its data line.

7. Firebase Integration

Firebase Realtime Database is used as the cloud backend between the ESP32 and the web dashboard. Sensor readings are stored using timestamp-based keys, allowing the dashboard to receive live updates and maintain historical data.

The database structure uses a relatively flat organization:

users/<uid>/bulb

settings/mode

settings/threshold

readings/<unix time>

Each reading contains temperature, humidity, light intensity and relay status. Firebase Authentication identifies authorized users and database rules control who can read or write different parts of the database.

8. Sensor Data Processing

The DHT11 provides temperature and humidity values. The LDR provides an analog value from the ESP32 ADC, ranging from 0 to 4095. Because LDR readings can be noisy, the firmware takes 15 samples with a short delay between samples and calculates an average value before using it for the control logic.

The DHT11 also requires an appropriate sampling interval, so readings are taken at approximately 2-second intervals.

9. Manual and Automatic Bulb Control

In manual mode, the user controls the bulb from the dashboard. When the dashboard changes the bulb state in Firebase, the ESP32 reads the updated value and switches the relay.

In automatic mode, the ESP32 compares the averaged LDR value with the configured light threshold. Based on this comparison, the relay is switched automatically.

If Wi-Fi or Firebase communication is lost, the relay is placed in the OFF state as a safety measure.

10. Real-Time Communication

A typical live-reading sequence is:

DHT11 and LDR measure the environment.

ESP32 processes and averages the sensor values.

ESP32 writes the reading to Firebase.

The Firebase real-time listener detects the new data.

The dashboard updates the temperature, humidity, light and relay status.

The same communication path works in the opposite direction for bulb control: dashboard → Firebase → ESP32 → relay → bulb.

11. Dashboard Integration

12. Important Implementation Points

DHT11 readings are handled at an appropriate interval of at least 2 seconds.

LDR values are averaged using 15 samples to reduce noise.

ESP32 ADC provides a 12-bit reading range of 0–4095.

ADC1 is used because ADC2 conflicts with Wi-Fi operation.

Relay control supports both manual and automatic modes.

The relay defaults to OFF when Wi-Fi or Firebase communication is unavailable.

NTP time synchronization is used for timestamp-based database records.

Firebase Authentication is used for authorized device/user access.

13. Testing & Results

Sensor reading interval: approximately 1 reading every 2 seconds.

Dashboard synchronization: approximately 1–2 seconds.

Relay response during testing: approximately 10 ms.

Firebase database read time: approximately 50–200 ms.

Real-time stream updates: generally less than 1 second.

14. Challenges & Solutions

Noisy LDR readings → reduced using 15-sample averaging.

DHT11 timing limitations → maintained the required sampling interval.

ADC behavior with Wi-Fi → used ADC1 GPIO34 instead of ADC2.

Deeply nested database structure → used a flatter Firebase schema for easier access.

15. Learning Outcome

This task helped me understand how real-world sensors, embedded systems, cloud databases and web dashboards can work together as one complete IoT system. I learned that sensor data is not always clean and that software filtering is important for reliable control.

I also learned how Firebase can act as the communication layer between hardware and a web interface, how real-time listeners remove the need for continuous page refreshes, and how authentication and database rules are important for securing IoT data and controls.

16. Final Outcome

A working cloud-connected environmental station was developed using ESP32, DHT11, LDR, relay and Firebase. The ESP32 measures temperature, humidity and light approximately every 2 seconds, sends the data to Firebase, and allows the Task 4 dashboard to display the readings in real time. The bulb can be controlled manually or automatically according to the light threshold, with a safe OFF state during communication loss.
