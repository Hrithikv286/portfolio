IoT project · Task 3

Voice Control with Google Assistant and IFTTT

This task adds a hands-free interface to the MQTT relay system from Task 2. A configured voice command triggers an IFTTT automation, which sends an HTTP Webhook request to Adafruit IO. Adafruit IO publishes the command over MQTT, and the ESP32 uses it to switch the relay. The core device-control system stays the same; voice automation becomes another way to send it a command.

End-to-end flow

Voice command → Google Assistant → IFTTT → Webhook → Adafruit IO → MQTT → ESP32 → relay → lamp

  1. The user speaks a configured command, such as a request to turn the lamp on or off.
  2. Google Assistant recognizes the command and activates the matching IFTTT applet.
  3. IFTTT sends an HTTP Webhook request carrying the selected value, such as ON or OFF.
  4. Adafruit IO updates the control feed and publishes the new value through its MQTT broker.
  5. The ESP32, already subscribed to that feed, receives the message and sets its relay-control GPIO.
  6. The relay switches the connected lamp. The device can publish its state back to a feed for cloud monitoring.

Role of each service

ComponentWhat it does
Google AssistantRecognizes a configured spoken command and starts the automation.
IFTTTConnects the voice trigger to an action and sends the Webhook request.
WebhookCarries the requested control value to the cloud service over HTTP.
Adafruit IOReceives the value, updates the feed, and routes it through MQTT.
ESP32 and relayTurn the received value into a GPIO output and switch the connected load.

How the command reaches the hardware

The voice assistant does not connect directly to the ESP32. IFTTT and the Webhook pass the command to Adafruit IO, while MQTT carries it from the broker to the subscribed device. This separates voice recognition, cloud automation, messaging, and physical control into clear stages.

An ON message asks the ESP32 to activate the relay; an OFF message asks it to deactivate the relay. The device can publish its resulting state separately. Reporting the state is useful because a voice trigger being recognized does not, by itself, confirm that the ESP32 received the message or that the relay changed.

What this adds to Task 2

Task 2 controls the relay from a cloud dashboard. Task 3 adds voice as another input while reusing the same Adafruit IO feed, MQTT connection, ESP32 firmware path, and relay output. The resulting system can support multiple control interfaces without creating a separate hardware-control chain for each one.

Engineering concepts demonstrated

  • Voice interaction: turning a spoken phrase into a defined device command.
  • Automation: using an IFTTT applet to connect an event to an action.
  • Web APIs: carrying a control value through an HTTP Webhook request.
  • Cloud messaging: relaying the value to a subscribed device through MQTT.
  • System integration: joining consumer services, cloud feeds, embedded firmware, and a physical output.

Reliability and safety

Voice control depends on internet access and successful operation of each service in the chain. If the assistant, IFTTT applet, Webhook, cloud feed, Wi-Fi connection, or MQTT session is unavailable, the command may not reach the ESP32. A dashboard or device-status feed provides a way to check the reported state; the system should also handle reconnects and unexpected command values.

The relay may switch a mains-powered load, but the ESP32 GPIO is only a low-voltage control signal. Mains wiring must remain isolated, enclosed, and rated for the load, with construction and inspection handled by a qualified person. Do not treat voice activation or a relay module as a substitute for electrical protection.

Outcome and next steps

The project connects a voice request to physical relay control through a sequence of automation and messaging services. It demonstrates how a new user interface can be added to an existing IoT architecture while keeping device control on the ESP32.

Further work could add commands for multiple devices, improve confirmation and error reporting, show connection health, and provide a manual fallback through the dashboard. Each added device or action should use clearly defined commands and report its state independently.
